# Дальнейшая разработка

Это предложения по этапам, а не согласованные сроки, бюджет или обязательства.

## 1. Выбор узкого пилота

Одна клиника, одно направление и один процесс: например, необработанные обращения или следующий этап плана лечения. Зафиксировать исходные показатели, ответственных, определения факта и критерии приёмки. Проверить, какие функции уже есть в установленной МИС клиента.

## 2. Проверка источников

Уточнить права и условия API конкретной МИС/CRM, телефонии и учёта оплат. Проверить доступность нужных полей и событий. Создать словарь показателей и сверку исходных записей с будущим интерфейсом.

## 3. Рабочий контур

Серверное хранение, аутентификация, реальные роли и разделение клиник; журнал действий; резервирование; повторяемая синхронизация; обработка дублей и ошибок. Публичный GitHub Pages остаётся витриной синтетического демо, реальные данные туда не загружаются.

## 4. Действия и ассистент

Подключать языковую модель после создания проверенного слоя данных. Ответ должен показывать основание и актуальность. Предложения действий требуют подтверждения сотрудника и проверки текущего состояния. Медицинские вопросы передаются специалисту. Уведомления и отправки включаются отдельным управляемым процессом.

## 5. Оценка пилота

Измерять выполнение задач, визиты и оплаты раздельно. Учитывать изменения трафика, доступного времени, команды и периода. Рост выручки сам по себе не доказывает эффект продукта. Коммерческую модель проверять оплатой пилота, трудозатратами поддержки и продлением.

## Поздние модули

Партнёрские направления, дополнительная аналитика, расширенная экономика, полноценные коммуникации. Полная ЭМК, ERP, склад, зарплата и собственная телефония не входят автоматически в первый продукт; их необходимость оценивается отдельно.
