# Паспорт и шаблоны результатов

## Содержание

- Комплект проекта
- Паспорт и состояния
- Аудит и рынок
- Аудитория и текстовый прототип
- Решения и материалы
- Итоговая передача

Использовать шаблоны как структуру заполненных материалов. Не передавать пустые шаблоны вместо результатов и не создавать файлы для незаказанных этапов. Выбирать подходящий формат по запросу пользователя.

## Комплект проекта

По умолчанию сохранять следующие артефакты в одной доступной папке проекта:

| Артефакт | Содержимое |
|---|---|
| `00-project.md` | Паспорт, этапы, основные решения, зависимости, открытые вопросы |
| `01-audit.md` | Аудит, охват, проблемы, сильные стороны, сохранение URL |
| `02-market.md` | Контекст рынка, выбор конкурентов, правила выбора, возможности |
| `03-competitors.xlsx` | Пять листов конкурентного анализа либо ссылка на заказанную онлайн-таблицу |
| `04-audience-jtbd.md` | Аудитория, основной JTBD, дополнительные задачи, маршруты |
| `05-text-prototype.md` | Карта сайта, готовые тексты по блокам, метаданные |
| `06-prototype/` | Входной файл/проект, необходимые ресурсы, исходники; ссылка на предпросмотр, если есть |

По желанию пользователя заменить Markdown на Google Docs или удобный отчет, сохранив содержание и связи. Ссылки на внешние материалы хранить в паспорте. Журнал проверок и передачу разместить в паспорте или отдельном коротком документе, если объем требует.

Сохранять итоговые артефакты по действующим правилам среды. Не считать временный локальный файл долговременным сохранением. Для существующего репозитория сохранять код там, а не дублировать весь проект в файловом хранилище.

```markdown

Обновлено: [дата]
Текущий сайт / новый проект: [...]
География и язык: [...]
Продукт и приоритетные направления: [...]
Бизнес-цель: [...]
Основное действие посетителя: [...]
Показатель успеха и источник / пока неизвестно: [...]
Источники трафика и готовность аудитории / гипотеза: [...]
Бренд, стек, интеграции и ограничения: [...]
Заказанный объем: [...]

| Этап | Статус | Результат/ссылка | Проверка готовности | Зависимости |
|---|---|---|---|---|
| Аудит | ... | ... | ... | ... |
| Рынок и конкуренты | ... | ... | ... | ... |
| Конкурентная таблица | ... | ... | ... | ... |
| Аудитория и JTBD | ... | ... | ... | ... |
| Текстовый прототип | ... | ... | ... | ... |
| Интерактивный прототип | ... | ... | ... | ... |

## Решения
[Реестр D-ID, основание и затронутые материалы]

## Неизвестное и допущения
[Что не подтверждено, как влияет, как проверить]

## Требуемые материалы
[Материал, назначение, формат, зависимый блок]

Применять статусы «не начато», «в работе», «готово», «готово с ограничениями», «блокировано», «не применимо». Статус «блокировано» использовать только для реально зависимой части; продолжать остальные разрешенные действия. При пользовательском поэтапном согласовании отдельно отмечать «ожидает решения пользователя» и фиксировать, какого именно.

Охват: [страницы/типы, сценарии, устройства, источники]
Ограничения: [...]

## Главные выводы
[3-5 наблюдений с последствиями]

## Что сохранить
[Предложение, материалы, страницы, функции, URL]

## Проблемы и решения
| A-ID | URL | Наблюдение/доказательство | Последствие | Исправление | Приоритет/уверенность |
|---|---|---|---|---|---|

## Карта сохранения и переноса
[Важные URL, намерение, действие и обоснование]

## Вопросы для проверки данными

```

### Обзор рынка

```markdown
# Рынок и конкурентное окружение
География, категория, сегмент, дата: [...]
Как искали и отбирали: [...]
Ограничения: [...]

## Как клиент выбирает решение
[Ситуации, альтернативы, критерии и источники]

## Кого сравниваем
| C-ID | Компания/URL | Тип | Почему подходит | Охват |
|---|---|---|---|---|

[Принцип, основание, как адаптировать, чем подтвердить]

```

Точные поля пяти листов таблицы брать из `research.md`; не дублировать несколько расходящихся схем.

## Решения и материалы

Использовать внутренние ID без сложной системы учета: `S` источник, `A` аудит, `C` конкурент, `O` наблюдение, `D` решение, `J` задача, `P` страница, `B` блок. При небольшом проекте разрешать простые явные ссылки вместо всех типов ID.

Реестр решений:

`D-ID | решение | основание/ссылка | J-ID | P-ID/B-ID | статус | проверка | что изменилось и почему`

Статусы решений: «предложено», «принято в рабочую версию», «подтверждено пользователем», «отклонено с причиной», «реализовано». Не называть решение подтвержденным пользователем без такого подтверждения. Автономно принятые обратимые решения отмечать как рабочие, не требуя формального утверждения каждого.

Реестр материалов:

`материал/факт | для какой страницы/задачи | источник/кто может предоставить | формат | что блокирует | временное правдивое решение`

Не считать отсутствующий материал фактом. Не вставлять внутренние заявки на материалы в клиентский интерфейс.

## Итоговая передача

```markdown
Готово: [конкретный объем и ссылки]
Ключевые решения: [что изменилось и зачем]
Проверено: [сценарии, экраны, состояния, результаты]
Ограничения: [что фактически не проверено/не подключено]
Нужно от клиента: [только существенные материалы/решения]
Для запуска: [CMS, интеграции, SEO-перенос и другие задачи по необходимости]
Следующее действие: [...]
```

Закончить передачей результата, а не вопросом о разрешении продолжить уже заказанную работу. Если пользователь заказал только часть процесса, завершить именно ее и назвать связь со следующим этапом без самовольного расширения объема.
