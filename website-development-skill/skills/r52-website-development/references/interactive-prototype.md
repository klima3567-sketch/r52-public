# Интерактивный прототип

## Содержание

- Выбор формата и объема
- Содержание и визуальная система
- Поведение элементов
- Проверки
- Передача результата

## Выбор формата и объема

1. Прочитать актуальные карту сайта, текстовый прототип, бренд и реестр решений. Составить список реализуемых страниц, типов и сценариев.
2. Выбрать формат под задачу и доступные инструменты. Для автономной проверки использовать HTML/CSS/JS без ненужной сборки; для существующего проекта соблюдать его стек и инструкции. Пользовательский выбор площадки имеет приоритет.
3. Реализовать настоящие файлы и открываемый интерфейс. Для локального варианта включить входной файл и все необходимые ресурсы; для опубликованного предпросмотра - сохранить исходники и дать ссылку.
4. Подготовить представительный объем: главная, уникальные приоритетные страницы и заполненные примеры повторяемых типов. Если сайт велик, явно назвать покрытие; не обещать весь каталог при реализации одной карточки.
5. Создать подробности по необходимости, но завершить каждый включенный основной маршрут. Для переходов к неразработанному разделу дать честное содержательное промежуточное состояние или исключить ссылку из активной навигации с объяснением в передаче. Не оставлять тупиковые CTA и пустые `href="#"`.
6. При разработке на внешней площадке читать ее актуальные инструкции и сохранять версии там, где требует среда. Публиковать в рамках существующего разрешения; учитывать явно заданные ограничения пользователя. Прототипом не заменять боевой сайт без поручения.

## Содержание и визуальная система

- Перенести готовые тексты, структуру и логику CTA; содержательные изменения фиксировать и синхронизировать с текстовым прототипом.
- Использовать фирменные материалы клиента или согласованное направление. При отсутствии бренда создать сдержанную согласованную систему шрифтов, цвета, сетки, отступов, кнопок, карточек и форм и назвать это рабочим решением в передаче.
- Применять доступные шрифты с надежным запасным вариантом; ограничить внешние зависимости, мешающие открытию прототипа.
- Делать значимую информацию текстом; не встраивать всю страницу картинкой. Использовать семантические заголовки, ссылки для переходов, кнопки для действий и подписи полей.
- Подбирать изображения и иконки по задаче и доступным правам. Не выдавать сгенерированное изображение за реальный объект, сотрудника, клиента или результат работы. При отсутствии реального фото выбрать нейтральный визуальный прием.
- Проверить контраст, видимый фокус, читаемость, расположение CTA, области нажатия и отсутствие перекрытий. Не фиксировать контакты/меню так, чтобы они закрывали форму и содержание.
- Добавлять анимацию, если она помогает восприятию и не мешает чтению. Учитывать `prefers-reduced-motion`, мобильную производительность и доступность содержания без анимации.
- Не показывать посетителю служебную методологию, номера решений, запросы недостающих материалов и комментарии исполнителя.

## Поведение элементов

| Элемент | Минимально работающее поведение |
|---|---|
| Навигация | Все включенные страницы/якоря открываются, активный раздел понятен, возврат возможен |
| Мобильное меню | Открытие, закрытие, выбор пункта; управление кнопкой с понятным состоянием |
| CTA | Соответствует подписи: переход, раскрытие или нужная форма; цель действия понятна |
| Вкладки/аккордеоны | Реально меняют состояние; содержание доступно; клавиатура и фокус работают |
| Модальное окно | Понятное открытие/закрытие, Escape, корректный фокус и возврат к инициатору |
| Контакты | Верные проверенные ссылки `tel:`, `mailto:` и мессенджеры, если данные доступны |
| Форма | Подписи, необходимые поля, ошибки, корректное состояние после проверки/отправки |
| Калькулятор | Обоснованная формула и вводы; предположения открыты; при отсутствии данных использовать иной сценарий расчета |
| Поиск/фильтры | Работа на включенных данных и понятное пустое состояние, если предусмотрены объемом |

Не создавать сложные элементы ради демонстрации. Если достаточно обычной страницы, не заменять ее модальным окном.

### Формы и интеграции

Если интеграция не настроена, проверять заполнение локально и показывать сообщение, например: «Данные заполнены корректно. Отправка в этой версии пока не подключена». Не писать «Заявка отправлена» и не сохранять контактные данные без необходимости. Не направлять демонстрационные обращения в рабочие почту/CRM.

Если реальная интеграция уже разрешена и входит в задачу, использовать согласованные поля, обработку ошибок, защиту и тестовый маршрут. Проверять отправку только в разрешенном окружении. Фактическое получение обращения подтверждать отдельно от срабатывания кнопки.

### SEO и техническая передача

Сохранить смысловую иерархию заголовков, черновые метаданные и карту адресов. Для доступного поисковикам предпросмотра предусмотреть исключение из индексации по возможностям среды; это не заменяет ограничение доступа. Не переносить запрет индексации на боевой сайт автоматически.

Не обещать работоспособную CMS, личный кабинет, оплату, CRM, аналитику и производственные редиректы, если реализован только интерфейс. Не встраивать секреты в клиентские файлы.

## Проверки

Сначала выполнить доступную сборку/проверку проекта, затем открыть реальный интерфейс. Не ограничивать проверку анализом кода. Использовать существующие средства автоматизации, если они доступны и уместны. Писать дополнительные тесты только для значимой логики; не создавать тесты, которые лишь повторяют разметку.

### Обязательный минимум

- Проверить минимум узкий мобильный экран около 360-390 px и широкий экран около 1366-1440 px; при сложной сетке проверить промежуточную ширину. Указать фактические ширины.
- Пройти каждый основной сценарий из карты аудитории: вход, понимание предложения, нужная страница, доказательство, действие, результат.
- Проверить основное меню, мобильное меню, все включенные ссылки и CTA, формы и состояния ошибок.
- Проверить клавиатурный доступ, видимость фокуса, порядок переходов и закрытие модальных окон, если они есть.
- Убедиться, что нет горизонтальной прокрутки, обрезанного текста, пропавших ресурсов, критических ошибок JavaScript и перекрытия содержимого.
- Сопоставить готовый интерфейс с текстовым прототипом и приоритетами; объяснить любое отклонение.
- Для автономной версии проверить открытие входного файла/локального сервера и относительные пути к ресурсам.
- При наличии анимации проверить уменьшенное движение и доступность содержания.

Фиксировать в журнале: сценарий, страница, среда/ширина, действие, фактический результат, статус, ограничение. Не называть проверенными состояния, которые фактически не открывались. Если визуальная проверка недоступна, передать рабочие файлы и прямо назвать непроверенные аспекты; не подменять это утверждением о полной готовности.

## Передача результата

Передать:

1. Открываемый прототип и исходники со всеми необходимыми ресурсами.
2. Перечень реализованных страниц, сценариев и взаимодействий.
3. Связь ключевых решений с аудитом, конкурентами и JTBD.
4. Краткий журнал фактических проверок и оставшихся ограничений.
5. Материалы/данные, которые нужны от клиента, и список задач для боевого внедрения.

Называть результат интерактивным прототипом, пока не выполнены и не проверены согласованные производственные функции. Разделять в передаче: реализовано; проверено; ограничено/не подключено; требуется для запуска. Не обещать конкретный прирост заявок без измерения.
